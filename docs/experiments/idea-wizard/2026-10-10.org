* Selection method

Scores are qualitative planning judgments about prospective benefit, informed
by the user’s goals and source inspection. They are not measured performance,
user-demand research or promises of universal reliability. Each dimension uses
1–5: robustness, reliability, performance, intuition, friendliness, ergonomics,
usefulness, appeal, accretive value and pragmatism. Weights are 2 for usefulness
and pragmatism, 1.5 for accretive value and 1 for the others. A score of 1 on
any dimension or average below 3 excludes a candidate. Remaining ideas are
ranked by weighted score; equal scores retain candidate order. Full vectors
and source evidence are in [[file:candidates.json][candidates.json]].

* Best five: rationale, implementation and proof

** 1. Preview and send the same frozen run plan

Make explicit context trustworthy at the moment it matters. A user can inspect the complete effective request, remove an item, and send exactly what was inspected. This directly advances ogent's founding constraint and reduces surprise when history, presets or project settings change.

Current evidence: ogent-context-preview rebuilds a rendered subtree payload; ogent-ui-request separately retains wire-prompt and send-args for retry. Context manifests already contain source, reason and hashes. The preview is not a committed snapshot of the final history/system/endpoint/tool selection.

Implementation: Introduce a versioned immutable plan after existing model/preset/endpoint validation, with prompt, history, system options, workspace, selected model, tool names/effects, inclusion reasons and hashes. Assign a durable UUID for the plan/request Org ID while preserving current process-local request IDs. Reuse the existing context manifest and retry snapshot. Exclude credentials, callable backend objects and transport handles from the serializable representation.

Native workflow: Render the plan in an owned Org reader with full searchable sections, per-item inclusion controls for handles/pins/history/attachments where applicable, source navigation, estimated token labels and a visible model/endpoint summary. Sending consumes that plan. An edit invalidates it and offers rebuild or the explicit frozen snapshot; no silent recomputation. Route ordinary prompts, source companions and fan-out through the same preparation boundary without forcing a preview on every send.

Risks: A second request engine or mutation of context would break retry/fan-out. Selection controls must alter a copied plan, not source text. Preview and send must agree at the semantic transport boundary; authentication headers and dynamic protocol IDs are intentionally excluded from the user payload comparison.

Refined contract: Refinement 1 - contract and feature preservation: Separate a frozen plan/content identity from each execution attempt UUID and each fan-out member Org ID. Retrying keeps semantic payload bytes but creates a fresh attempt/destination; retain old process-local IDs for compatibility. Keep send-consumption state outside the immutable plan and reject reentrant double-submit unless the user deliberately reruns. Include explicit omitted-history/inclusion reasons and a source fingerprint in the plan.

Acceptance: Previewed prompt/history/system/model/tools equal the semantic request observed by the owned HTTP fixture; changing a source or preset after preview triggers a clear stale-plan choice. Fan-out members share one context snapshot. A cancelled preview sends nothing and leaves focus/source text intact.

Independent verification: ERT: empty, Unicode and multiline inputs; changed source/preset/history; read-only source; inclusion toggles and UUID collisions; immutable retries. E2E: real gptel Chat Completions and Responses fixtures compare serialized semantic payloads with the displayed plan, including source companion and fan-out paths.

** 2. Ship a no-login interactive practice workspace

Let a new user feel the native workflow before configuring a provider: context, streaming, a tool decision, an edit and recovery. It is also a reproducible support and regression workspace, so this small product feature supports several later ideas.

Current evidence: README onboarding guides provider authentication. make demo opens an Org file without loading ogent. Actual no-provider HTTP/CLI and GUI fixtures exist under test/offline and docs/experiments/emacs-workflows, but are developer-specific scripts rather than a supported first-use command.

Implementation: Extract a reusable, bounded fixture lifecycle that allocates an owned temporary Org workspace and loopback backend/CLI executable. Reject non-fixture HTTP hosts and executables, load real runtime dependencies, and track cleanup. Provide deterministic response/error/tool/slow-stream scenarios with fixed synthetic data; isolate all analytics, ledgers, approval settings and conversation stores.

Native workflow: Add an autoloaded ogent practice entry command with a short Org lesson and reachable actions. Load ogent explicitly, explain that replies are simulated, demonstrate frozen-plan preview, attach/type/submit, approve/deny, edit acceptance and cancel/retry. Starting and exiting preserve the user's backend, model, keys, files and window configuration. Missing fixture prerequisites produce precise remediation.

Risks: Reusing a fake API key without a host guard risks external calls. Avoid globally changing Customize values or silently saving the practice workspace to real stores. A learning command must work from an installed package as well as a checkout, or clearly document the supported development-only fixture requirement.

Refined contract: Refinement 1 - contract and feature preservation: Choose and document the smallest supported fixture runtime before exposing the command. Ship necessary fixture assets in the installed package, or make checkout-only limitations explicit instead of implying a clean install works. Isolate analytics/ledger/Customize and restore preexisting backend/window state even when startup fails halfway.

Acceptance: A clean Emacs session completes the guided workflow with no provider credentials and zero non-loopback inference requests. Quit and failure clean up owned processes/timers/temp stores and restore the prior configuration. Installation requirements and simulated behavior are stated before the first action.

Independent verification: ERT: environment save/restore, missing prerequisites, port/server startup failure, child timeout, repeated start/stop and foreign-store tripwires. E2E: actual keyboard lesson in vanilla and Evil, with real gptel and local fixture CLI; assert complete final output and no leaked requests/processes.

** 3. Apply a reviewed edit set as one buffer transaction

Make a reviewed change set behave as a single deliberate action across files. The user can understand the whole proposed change and avoid discovering that only half of it landed after a hook or buffer error.

Current evidence: ogent-edit-diff-accept-staged preflights all proposals, then applies atomic-change-group separately for each source buffer and records resolutions after each group. Earlier buffers can already be accepted if a later buffer throws. Existing stale-match and per-buffer atomicity fixes remain valuable.

Implementation: Add a request-scoped edit transaction over participating live buffers: preflight exact source contents/overlap, prepare and activate all change groups, perform replacements, cancel every group on failure, and publish accepted statuses/analytics/ledger only after successful commit. Keep individual acceptance/rejection and existing smerge/overlay paths. Specify the boundary as buffer edits, without promising atomic disk saves, arbitrary hook side effects or Git operations.

Native workflow: Show files, staged proposal count and transaction status in the existing review reader. Offer accept-selected-as-set with an explicit buffer transaction label; refuse mixed request sets or define an explicit grouped policy. Retain full diffs, jump-to-source and read-only staging. If offering undo-set, guard inverse edits against subsequent user changes and explain conflicts instead of overwriting them.

Risks: Cross-buffer undo is not the same as per-buffer undo. Hooks can have external effects that Emacs change groups do not roll back. A source buffer dying or changing during review must leave every still-owned proposal unresolved and every surviving buffer unchanged on failure.

Refined contract: Refinement 1 - contract and feature preservation: Delay every proposal resolution, acceptance signal and ledger publication until all participating buffer change groups commit. Define a rollback procedure even when a modification hook raises during application; external hook side effects and disk saves are outside the promised buffer transaction. Individual review and rejection remain available.

Acceptance: An injected failure in the second buffer leaves all source buffers, staged states and accepted-event counts unchanged. A successful set changes every intended buffer, resolves each proposal once and preserves normal single-edit acceptance. No implicit save/commit occurs.

Independent verification: ERT: stale/ambiguous/overlapping matches, duplicate proposals, killed/read-only buffers, narrowing, Unicode and injected before/after-change failures. E2E: a two-file edit through the actual registered write/edit tool path, stage/review/accept or reject, verify all buffers and exactly-once ledger/analytics; exercise undo conflict if shipped.

** 4. Recover drafts and interrupted runs after Emacs restarts

Protect the work around a request as well as its final answer. On reopening Emacs, a user should recover a draft and see what was interrupted, with enough context to choose a safe next step.

Current evidence: ogent-session-save persists transcript text and metadata. Composer draft/attachments are buffer-local; active requests, retry history, markers and watchdogs are in memory. Existing CLI resume and immutable retry do not establish crash recovery of a native draft or pending tool decision.

Implementation: Provide opt-in, versioned Org checkpoints for draft text, attachment references, stable plan/request IDs, validated serializable snapshot data, partial response and known lifecycle/effect events. Use owned atomic file replacement and explicit retention. Whitelist fields; never persist keys, auth headers, backend function objects, live processes or executable Lisp. Reopen old session formats unchanged.

Native workflow: Offer a local recovery reader on demand that restores editable drafts and labels interrupted runs without replaying them. Retry is a new explicit request from the saved snapshot. When a tool may have changed external state before interruption, show the uncertainty and evidence and require an explicit recovery choice. Reuse grounded CLI resume for supported adapters; do not pretend a dead gptel FSM can resume.

Risks: A crash between a write and its terminal ledger entry leaves an unknown outcome. Automatic replay could duplicate an effect. Restoring missing/moved attachments or incompatible schema requires an actionable partial recovery path. Checkpoints can contain private prompt text and need visible location/retention/delete controls.

Refined contract: Refinement 1 - contract and feature preservation: Debounce/bound checkpoint writes without losing the last completed boundary; record draft ownership and retention explicitly. Reopening is data parsing only. Distinguish never-sent, partially streamed and unknown tool outcomes. Missing attachments remain visible references, and saved executable/callable Lisp is rejected rather than restored.

Acceptance: A fresh Emacs process recovers a Unicode multiline draft and attachment list, displays a partial interrupted answer and performs zero network/tool execution on load. User-selected retry retains the saved semantic context under a new run ID. Corrupt/unknown versions do not execute code or destroy earlier records.

Independent verification: ERT: every checkpoint transition, truncation/corruption, missing files, retention, legacy sessions and unknown pending effects. E2E: terminate and restart an owned Emacs fixture at draft, streaming and tool-pending boundaries; assert restored state, zero automatic execution and explicit immutable retry.

** 5. Offer workspace and session scoped approval grants

Reduce repeated prompts while letting the user approve a scope they can understand: this invocation, or a stated invocation/target rule for this workspace and session. Keep the existing explicit persistent option available.

Current evidence: ogent-tool-allow-list stores global string patterns; the always choice derives a tool-wide or first-command-word pattern and saves it in Customize. The new reader explains that actual scope, but does not add bounded workspace/session grants.

Implementation: Add structured grants with canonical workspace, canonical tool identity, explicit argument/target matcher, effects/schema fingerprint, session or expiry boundary and an explainable decision result. Resolve symlinks and outside-workspace targets before matching; decline bounded grants when identity/scope is uncertain. Preserve legacy configured patterns as legacy global grants, without silently broadening, converting or deleting them.

Native workflow: Show the exact grant rule, workspace, lifetime and effect before saving it. Add reachable bounded approval choices and an inspect/revoke view. Use the same decision boundary for native gptel, SDK, MCP and recorded replay. Retain single invocation approval, denial, C-g denial and existing allow/deny precedence.

Risks: A shell command prefix is not a confinement boundary. Expiry, clock rollback, changing tool schema/effects and nested workspaces must invalidate or fail a bounded match. Legacy rules can be broad and must remain visibly identified rather than hidden behind new guarantees.

Refined contract: Refinement 1 - contract and feature preservation: Pass a trustworthy canonical execution workspace into policy matching from every caller, including SDK/no-prompt and MCP paths; current-buffer/default-directory guesses are insufficient in delayed callbacks. Keep legacy global patterns visibly legacy. Bound grants to exact declared arguments/targets; an executable prefix does not confine arbitrary shell commands.

Acceptance: A bounded grant matches only its displayed workspace/invocation rule during its declared lifetime and stops matching after expiry, revocation or effect/schema change. An unrelated project and outside target still require a decision. Existing global configuration retains its documented behavior.

Independent verification: ERT: symlinks, path traversal, nested workspaces, case/platform normalization, malformed grants, expiry/clock rollback, canonical aliases, precedence and legacy patterns. E2E: actual gptel confirmed tool calls across two owned workspaces, grant/reuse/revoke/deny with execution and ledger counts; no real commands/providers.

** 15. Verify spoken states with Emacspeak and reduced motion

Extend accessibility evidence to people consuming the interface through speech, where a visible icon or header line may not announce the state. Respect users who prefer stable presentation during long background work.

Current evidence: Native audit checked meaningful text, keyboard access, larger fonts, terminal and ASCII. Its report explicitly says screen-reader compatibility is untested. Some state cues are virtual header/margin overlays or animation rather than ordinary buffer text.

Approach: Audit actual Emacspeak navigation/announcement behavior on fixture requests, approvals, errors and completion with recorded versions. Expose a small optional semantic announcement hook and local reduced-animation setting as necessary, using state words and concise summaries without reading private tool arguments automatically. Provide readable current-state/detail commands and opt-in announcements for pending decision, failure, cancellation and completion. Verification: ERT: semantic announcement events exactly once, privacy-safe summaries, optional reader absence, reduced-motion timer cleanup.
